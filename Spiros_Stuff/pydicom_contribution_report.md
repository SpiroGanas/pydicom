# How an Intermediate Python Developer Can Contribute to pydicom

*Report based on a review of the repository at commit `6f92f30` (version `3.1.0.dev0`).*

## 1. Project snapshot

| Item | Detail |
|---|---|
| What it is | Pure-Python library for reading, modifying and writing DICOM medical-imaging files |
| Size | ~38k lines in `src/pydicom/*.py` (top level), plus subpackages; ~50 test modules in `tests/` |
| Python support | 3.10 – 3.14, zero hard runtime dependencies (NumPy and image codecs are optional) |

## 2. Ground rules to know before starting

These come from `CONTRIBUTING.md` and `.github/PULL_REQUEST_TEMPLATE.md` and shape what a good first contribution looks like:

1. **Fork → feature branch → PR** (draft first, mark ready when finished). PRs are squash-merged and usually need two approvals.
2. **AI-only PRs are rejected.** The PR template requires a human-written summary and line-by-line review of any AI-assisted code. Write your own summary.
3. **Bug fixes need a regression test that fails before the fix.** New features need tests and docs.
4. **Type hints are required** (`mypy` runs with `disallow_untyped_defs`), and docstrings use **NumPy style**.
5. **Coverage must not drop** — new lines should be covered.
6. **Run `pre-commit`** (ruff, black, mypy, typos) before committing.
7. **Add a release note** entry under `doc/release_notes/` (currently `v3.1.0.rst`) for user-visible changes, referencing `:issue:` / `:pr:`.
8. Don't edit the generated `_*_dict.py` files directly — change the generator under `util/` instead.

## 3. Recommended contribution paths (ranked)

Ranked by *value to the project* × *fit for an intermediate developer* × *likelihood of being merged*.

### 🥇 Tier 1 — Best starting points

#### 3.1 Triage and fix labelled GitHub issues (bug fixes with regression tests)
- **Why it's the best fit:** The recent history is dominated by exactly this kind of change — small, well-scoped fixes with a linked issue (e.g. the GB2312 charset fix `#2385`, the LUT clamping fix `#2382`).
- **How:** Browse open issues on GitHub filtered by labels such as `good first issue` / `bug`; reproduce with a minimal script; add a failing test in the matching `tests/test_*.py`; fix; add a release-note line.
- **Skills used:** debugging, reading unfamiliar code, `pytest`, careful reading of the DICOM standard (PS3.x) for the relevant part.
- **Tip:** Comment on the issue first to avoid duplicated effort; reproducing an issue and confirming it still occurs on `main` is itself a useful contribution.

#### 3.2 Improve test coverage and test quality
- **Why:** Maintainers explicitly require "coverage the same or better," and there is at least one acknowledged gap: `dataelem.py:301` carries `# TODO: test wado-rs retrieve wrapper` (the `bulk_data_uri_handler` path in `DataElement.from_json`).
- **How:** Run `pytest --cov=pydicom --cov-report=term-missing`, pick modules with missing lines (start with the smaller ones: `util/`, `cli/`, `hooks.py`, `misc.py`, `fileutil.py`), and add targeted tests. Low risk of breaking anything, easy to review.
- **Bonus:** `tests/` has ~50 files; consolidating repeated setup into fixtures or `parametrize` is welcome when it clarifies intent (keep PRs small).

#### 3.3 Documentation fixes and additions
- **Why:** Low barrier, always needed, and it teaches you the API surface. Docs build with Sphinx (`doc/`), and the PR checklist requires "no warnings during build."
- **Ideas:**
  - Proofread guides in `doc/guides/user/` and tutorials in `doc/tutorials/` (check that code samples still run on 3.x — doctests are executable via `pytest doc/*.rst`).
  - Fill in missing "Examples" sections in docstrings of public methods (CONTRIBUTING requires usage doctests "when appropriate").
  - Add a new gallery example in `examples/` (e.g. under `metadata_processing/` or `input_output/`) demonstrating a real workflow — the contributing guide asks for examples that show why a feature is useful compared with alternatives.
  - Clean up stale references left over from the Python 2 era or pre-3.0 APIs (the most recent commit is exactly this type of cleanup).

### 🥈 Tier 2 — Good once you have a first PR merged

#### 3.4 Typing improvements
- `mypy` is configured strictly, and there are ~49 `# type: ignore` comments across `dataset.py`, `valuerep.py`, `filewriter.py`, `fileutil.py`, `pixels/…` and `cli/main.py`. Each one is a small, self-contained puzzle: can it be removed with a better annotation, a `Protocol`, an overload, or `TypeGuard`?
- Also: `pixel_data_handlers/pillow_handler.py` is excluded from mypy (legacy, being removed), so focus on the live `pixels/` package.
- **Skills used:** generics, `typing` module, `Protocol`, `overload`. Great way to learn the core classes.

#### 3.5 Python-version modernisation (explicit TODOs)
Minimum Python is already 3.10, and there are TODOs waiting on newer features:
- `pixels/common.py:289` — "Python 3.11 switch to `StrEnum`" (and `:310` "no longer needed if StrEnum")
- `pixels/common.py:690` — "Python 3.11 use `typing.Unpack`"
- `pixels/encoders/native.py:54` — "Python 3.11 switch to using `zlib.compress()`…"

⚠️ **Check first:** `requires-python` is currently `>=3.10`, so these are only actionable when the project raises its minimum to 3.11 — ask maintainers in an issue before implementing. Also use `ruff`'s `UP` rules to find other modernisation opportunities (f-strings, `|` unions, etc.).

#### 3.6 CLI and utility enhancements
- `src/pydicom/cli/` (`show`, `codify`) and `src/pydicom/util/` are small, self-contained modules with clear inputs/outputs — a good place for a first *feature* (new option, better error message, better output formatting).
- The CLI supports **plugin subcommands** via the `pydicom_subcommands` entry-point group in `pyproject.toml`; building a new subcommand (e.g. a `summary`/`diff` helper) is a good exercise, but propose it in an issue first.
- Tests are in `tests/test_cli.py`, `tests/test_util.py`.

#### 3.7 Performance work with benchmarks
- The repo has an `asv` setup (`asv.conf.json`, `benchmarks/` — encaps, RLE encode/decode, nested sequences, pixel utils, numpy handler).
- Profile common operations (e.g. `dcmread` on large datasets, sequence iteration, `Dataset.__getitem__`, encapsulation helpers), add a benchmark, and submit optimisations **with before/after numbers**. Requires discipline: performance PRs are only accepted if they don't hurt readability or correctness.

### 🥉 Tier 3 — Higher effort / higher context required

#### 3.8 Pixel data plugin work (`pixels/decoders`, `pixels/encoders`)
- The plugin architecture (Pillow, pylibjpeg, pyjpegls, GDCM, native RLE/uncompressed) is where much of the active feature work happens (see v3.1.0 release notes). Contributions here need NumPy comfort, familiarity with DICOM transfer syntaxes and the ability to install optional codecs; tests are in `tests/pixels/`.
- Good entry points: improving error messages when a plugin is missing, adding test coverage for rarely-used paths (e.g. 1-bit, big-endian, float pixel data — all recently-fixed areas), and edge cases in `pixels/utils.py`.
- `pixels/processing.py:135` has a `TODO: Requires greyscale visualisation pipeline` — supporting *Supplemental Palette Color LUT* in `apply_color_lut` is a larger feature; discuss with maintainers first.

#### 3.9 Helping with the v4.0 deprecation clean-up
- ~14 `# TODO: Remove in v4.0` markers (e.g. `dataset.py`, `filewriter.py`, `pixels/decoders/base.py` for `as_frame`, plus whole legacy modules `pixel_data_handlers/` and `encoders/`).
- **Do not remove these now** — removal is a breaking change tied to a major release. Valuable preparatory work, however, is: auditing that every deprecated API emits a `DeprecationWarning` with a helpful message, has a test asserting the warning, and is documented with its replacement.

#### 3.10 DICOM standard updates (generated dictionaries)
- `_dicom_dict.py`, `_uid_dict.py`, `sr/_cid_dict.py`, etc. are produced by scripts in `util/generate_dict`, `util/generate_uids`, `util/generate_cids`. The v3.1.0 notes say the dictionary is at DICOM 2024d, so refreshing it against a newer standard release is periodically needed.
- Suited to someone who likes data wrangling and standards documents; ask maintainers whether an update is already underway before starting.

## 4. Suggested first-30-days plan

| Week | Goal | Concrete actions |
|---|---|---|
| 1 | Set up & orient | Fork, `pip install -e .` plus dev/test extras, `pre-commit install`, run the full test suite and `mypy`; skim `doc/tutorials/contributing_code.rst`; read `Dataset`/`DataElement` source and the "Dataset basics" tutorial |
| 2 | First PR (tiny) | Fix a typo/docstring/doc example, or add a missing test for an uncovered line — goal is to learn the PR/CI/review loop |
| 3 | Second PR (bug fix) | Pick one `good first issue`/`bug`; reproduce → failing test → fix → release note |
| 4 | Third PR (quality) | Remove 2–3 `# type: ignore` comments properly, or add a gallery example / CLI improvement discussed in an issue |

## 5. Practical tips

- **Search before filing/working:** check existing issues and PRs (CONTRIBUTING asks for this); comment "I'd like to work on this" to claim an issue.
- **Keep PRs small and focused** — one concern per PR; squash-merge means your commit messages get combined, so keep them concise and descriptive (e.g. `Add warning when saving compressed without encapsulation`).
- **Use a draft PR** if you want early feedback.
- **Read the DICOM standard section** relevant to your change (the public NEMA site hosts PS3.x); many "bugs" are about conforming to a detail of the standard, and maintainers will ask for the citation.
- **Test with real-looking data:** the repo ships many test datasets (`pydicom.data`); prefer them to hand-crafted bytes where possible, and avoid adding large new binary files.
- **Be careful with backward compatibility** in `Dataset`, `DataElement`, and I/O functions — users depend on subtle behaviours.
- **Optional dependencies:** many tests are skipped unless NumPy / Pillow / GDCM / pylibjpeg / pyjpegls are installed. Install what your change touches so you test the code you modified (CI covers the matrix).
- **Disclose AI assistance honestly** and make sure you understand every line you submit; the project will close AI-only PRs.

## 6. Quick reference commands

```bash
# setup
git clone https://github.com/<you>/pydicom && cd pydicom
pip install -e .
pip install pytest pytest-cov ruff black mypy pre-commit numpy
pre-commit install

# tests and coverage
pytest tests/test_dataset.py -x
pytest --cov=pydicom --cov-report=term-missing tests/

# quality gates
ruff check .
black src/pydicom tests
mypy
pre-commit run --all-files

# benchmarks (needs asv)
asv run --quick

# docs
make -C doc html
```

## 7. Caveats of this review

- Findings are based on the repository contents only (code, config, docs, git log). I did **not** inspect the live GitHub issue tracker, so check there for the current list of `good first issue` / `help wanted` items.
- The `TODO` counts and `type: ignore` counts were obtained with simple text searches and are approximate.
- I did not run the test suite or measure coverage; coverage-gap suggestions above are directions to investigate, not measured results.
